# Windows 更新恢复与旧进程边界

## 当前范围与发布状态

本分支的 Windows x64 迁移候选是 `distribution: direct`：GNU 历史文件名的 ZIP 保留旧更新器接受的文件集合与 schema 1，新增 `direct_runtime` 描述；其中的主 EXE 与原生 MSVC 包的 EXE 字节完全相同。没有 GNU wrapper、首次启动解压、第二次下载或包内安装回调。旧 GNU 更新器仍只提取并替换主 EXE。

[发布策略](../.github/release-policy.json) 的 `windows_x64_msvc.enabled` 仍为 `false`。代码修改、源码级复现、测试程序编译和正式发布是不同状态，不能互相替代。本文记录恢复约束与验收要求，不表示已批准或启用正式迁移。

[原迁移说明](WINDOWS-MSVC-MIGRATION.md) 的主体保留了 `embedded_runtime` 历史设计。其 wrapper、内嵌 ZIP、首次展开和独立子目录行为不适用于当前 `direct_runtime` 路径。

## 风险一：两次改名之间主程序路径可能缺失

原来的当前 Windows EXE 事务先把目标改名为备份，再把暂存候选改名为目标。第二步失败时可以尝试回滚，但如果进程恰好在两步之间被终止，回滚代码不会执行，主程序路径就会缺失。普通错误回滚测试通过不能排除这个中断窗口。

当前加固方向是先完成同目录候选的写入与同步，保留旧映像的硬链接备份，再使用 Windows `FileRenameInfoEx` 的替换/POSIX 语义一次切换目标名称。旧目标不先改名离开；文件系统或系统不支持该原子替换时明确失败，不退回先删目标、两次改名或直接复制覆盖。相关实现和原生 Windows 测试完成后，才能确认所测文件系统上的支持情况。

这项保证针对执行新代码的更新事务。不可变 GNU 1.0.45 仍使用历史 copy → rename → copy → rollback 实现，不能凭新源码宣称它获得了原子性。一次名称切换也不等同于任意断电、磁盘故障、文件系统故障下的完整持久性保证。

## 风险二：驻留 GNU 1.0.45 可以晚到覆盖较新版本

这是历史实现的真实边界，不是新版锁内版本比较能够修补的旧进程：

1. GNU 1.0.45 进程先选择、下载、提取并检查候选版本 N，此时还没有取得安装锁。
2. 另一个写入者先安装较新版本 N+1，然后释放 `grok-zh.exe.update.lock`。
3. 延迟的旧进程取得同一把锁，却不重新读取磁盘版本，直接激活 N。因此锁能避免同时写入，不能保证按版本从旧到新提交。

新更新器的锁内版本检查只能约束执行该检查的写入者。新程序已经启动、有人仍持有新 EXE 的允许删除共享读句柄、一次成功的版本探测，或新更新器曾经取得过锁，都不能永久阻止驻留旧进程稍后覆盖它。也不能把磁盘路径当前返回的 `--version` 当成早先启动的进程自身版本。

### 受支持的切换操作

- 安装或迁移前，保存工作并退出该安装的所有旧 GNU 会话及其更新进程。切换期间不要从旧路径、旧备份或旧终端重新启动旧程序。
- 旧进程退出后，运行当前完整安装器安装经过验证的 MSVC 包。安装器的活动进程预检应拒绝目标安装仍被相关进程使用的情况，给出 PID 并请用户自行退出；无法可靠识别相关进程路径时应停止，而不是猜测不存在。
- 进程预检是前置保护，不是原子进程隔离。扫描后重新启动旧程序的竞态仍然存在；不承诺可以在任意旧进程持续运行或任意启动旧程序的环境中完成无降级切换。安装器不应强杀会话，也不应改动杀毒、防护策略、ACL 或建立长期后台守护来掩盖这个边界。
- 完成切换并确认旧进程全部退出后，再从目标安装路径启动程序并检查实际版本。如果已发生晚到覆盖，先停止残留旧写入者，再用当前完整安装器重装目标版本；不要认为新程序的防降级代码会追溯撤销旧程序已经完成的写入。

历史 EXE-only 更新不会执行新版包内安装器，因此不能假定新增安装器预检自动覆盖了所有旧客户端的在线自更新路径。旧事务完成后到第一次正常启动新版之前同样不能假定已有新版保护。直接替换旧 EXE 的自动迁移若没有先满足旧写入者退出的条件，仍须明确保留这项风险，不能标为“彻底修复”。

完整安装器使用目录级暂存/切换，而旧锁文件位于被替换目录内部。某些 Windows 环境会拒绝重命名含活动子文件句柄的目录，因此不能简单地跨整个目录替换持有旧锁，并据此声称消除了驻留旧进程问题。重新创建同名锁文件也不等于保持同一个锁对象。

## 风险三：PowerShell 流水线停止可能绕过 catch

原完整安装器将旧目录移到 `.previous.*` 的操作位于内层 `catch` 保护范围之外；流水线停止还可能不执行预期的 `catch`。如果 `finally` 只删除暂存目录，用户取消后就可能只剩备份目录，没有原安装路径。

恢复处理需要放在 `finally` 中，并按磁盘事实判断，而不是只依赖赋值完成的布尔状态：目标缺失且本次旧备份仍存在时，尝试恢复旧目录；恢复失败、路径被其他内容占用或提交状态无法确认时，保留可恢复副本并输出准确路径，不继续清理唯一可用程序。普通失败和 runspace `Stop` 都需要覆盖。

这种恢复只适用于执行环境仍有机会运行清理代码的停止或异常。强杀整个 PowerShell 宿主、系统崩溃或断电不会保证执行 `finally`。这类中断后应先确认没有旧安装/更新进程仍在写入，再检查目标目录以及对应的 `.previous.*`、`.stage.*` 目录；保留无法确定归属或完整性的内容，使用已验证的完整安装包恢复，不能先删除全部备份再尝试重装。共享 `GROK_HOME`、账号、配置及会话数据不属于程序目录回滚范围。

## 验收证据与尚未证明的事项

### 历史写入者负向测试

[`legacy_race_tests.rs`](../.github/scripts/direct-transaction-validation/legacy_race_tests.rs) 直接调用从不可变历史源码逐字提取的锁与激活函数：先准备真实 MSVC 1.0.104 安装副本与真实 GNU 1.0.45 候选，检查候选版本；较新写入者持锁时旧写入者不能取得锁，但释放后旧函数可以把目标换成 GNU 字节。新 EXE 的共享读句柄保持原有字节，并不阻止目标名称被替换。

该例的 `legacy-delayed-writer-overwrite.json` 只有在成功复现覆盖时才记录 `status: PASSED` 和 `risk_reproduced: true`。这里的“通过”表示负例揭示了风险，不表示风险已修复。它是候选验证之后的激活边界复现，不测试自动版本选择，不声称 GNU 1.0.45 的自动策略会选择自身版本，不是未修改旧 GNU EXE 的在线升级，也不是运行中的真实旧产品进程。

### 必需的原生 Windows 验证

- 在旧两次改名算法的目标移出后终止独立测试进程，复现主路径缺失；对新算法在备份后、原子切换前后分别终止测试进程，核对目标始终是完整旧文件或完整新文件。运行中映像、共享句柄、长路径和不支持替换语义的失败路径分别验证。
- 当前自动更新在同一安装锁内重新探测目标，保留已安装的更高版本；与历史负例并列，不能只测试新代码而推断旧代码安全。
- Windows PowerShell 5.1 与 PowerShell 7 对旧目录移动后、暂存目录提交前后的 runspace `Stop` 注入，检查恢复后的实际目录、可执行文件与被保留备份。另测恢复失败时不删除恢复材料。
- 活动旧进程预检覆盖目标安装进程、已重命名的映像、无关安装、映像路径不可读以及进程刚好退出的情况；仍保留扫描后启动旧进程的已知边界。

本轮新加固和故障注入的原生 Windows 结果在取得对应 CI/验收日志前均为**待验证**。Linux 静态检查、源码生成成功、历史通过数或测试 EXE 编译成功都不等于这些 Windows 分支已执行。验收材料应同时记录测试源码、产品输入哈希、实际用例与逐项结果；不使用旧结果填补新场景。

正式启用前还需要获准执行的真实历史客户端更新链及不同 MSVC 版本的后续升级验收。仅有同版本重装、模拟传输、共享文件句柄或历史源码等价测试，不足以宣称这些发布链路已经通过。
