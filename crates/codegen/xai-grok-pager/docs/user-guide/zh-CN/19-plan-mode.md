<a id="plan-mode"></a>
# 计划模式

计划模式是一种结构化规划阶段：代理在编写任何代码之前探索代码库并设计实现方案。对于正确方案存在真实歧义的任务，先获得你的输入可避免大量返工。

---

<a id="what-plan-mode-does"></a>
## 计划模式的作用

计划模式处于活动状态时，代理会：

1. 读取并搜索代码库，以了解现有模式和架构
2. 设计实现方案，并将其写入计划文件
3. 可能使用 `ask_user_question` 澄清具体问题
4. 调用 `exit_plan_mode` 呈现计划，等待你批准

除计划文件外，计划模式是只读的：计划文件编辑（会话目录中的 `plan.md`）会自动获批，任何其他文件的编辑都会被直接拒绝——工具调用会失败，并用简短消息指出计划文件是唯一可编辑路径。这一规则在所有权限模式下都成立，包括始终批准模式。将规划与实现分开，便于你在写入任何代码前审查并纠正方案。

---

<a id="how-to-enter-plan-mode"></a>
## 如何进入计划模式

<a id="agent-initiated-entry"></a>
### 代理主动进入

当代理判断任务存在真实歧义时，会进入计划模式。它会调用 `enter_plan_mode` 工具；该工具需要你批准后，计划模式才会启用。若你拒绝，代理会留在普通模式。

**适合触发计划模式的情况：**

- “为应用添加用户身份验证”——确实存在歧义（会话还是 JWT、令牌存储方式、中间件结构）
- “重新设计数据管道”——属于大规模重构，方案错误会浪费大量工作
- “为 API 添加缓存”——有多种合理方案（Redis、内存或基于文件）
- “添加实时更新”——需要做架构决策（WebSockets、SSE 或轮询）

**不适合计划模式的情况：**

- “为用户资料添加删除按钮”——实现路径清晰
- “修正 README 中的拼写错误”——直接修改即可
- “更新 API 的错误处理”——先开始工作，需要时再提出具体问题
- “我们可以做搜索功能吗？”——用户想开始工作，而不是先制定计划

<a id="user-initiated-entry"></a>
### 用户主动进入

你可以通过两种方式自行进入计划模式：

- **`/plan`** ——进入计划模式。发送下一条提示时计划模式才会启用。运行 `/plan <description>`，可以一步进入计划模式并用该描述开始一个回合。
- **Shift+Tab** ——循环切换会话模式：普通、计划、始终批准，然后回到普通。从普通模式按一次会到计划模式。

计划存在后，运行 **`/view-plan`**（别名为 `/show-plan`、`/plan-view`）即可重新打开其已保存的预览。

<a id="the-plan-file"></a>
## 计划文件

计划会写入会话目录中的 `plan.md`（`~/.grok/sessions/<cwd>/<session-id>/plan.md`，其中 `<cwd>` 是编码后的目录名，而不是字面路径）。

计划文件包含：

- **Context** 部分，解释为何要进行这项变更
- 推荐方案（而不是罗列每个备选方案）
- 需要修改的关键文件路径
- 可复用的现有函数和工具，以及它们的文件路径
- 验证部分，说明如何端到端测试变更

---

<a id="plan-approval"></a>
## 计划批准

完成规划后，代理会调用 `exit_plan_mode` 工具。该工具从磁盘读取计划文件，TUI 会打开可滚动的计划预览，底部显示操作栏。

如果代理退出时没有写入计划（`plan.md` 为空或缺失），同样会打开批准界面，并显示清晰的空状态消息。你可以批准并开始实现、要求修改（让代理回到规划阶段），或退出。在精简模式中，空状态提示会写入滚动区，控件条标题显示为 **No plan written yet**。

<a id="reviewing-the-plan"></a>
### 审查计划

用方向键或 `j`/`k` 滚动计划。操作栏显示以下快捷键：

| 快捷键 | 操作                                                                                               |
| ------ | ---------------------------------------------------------------------------------------------------- |
| `a`      | 批准计划并开始构建。有待处理评论时，显示为 `approve w/ comments`，并将评论一并随批准发送。 |
| `s`      | 请求修改。焦点移到提示框，你可以输入修订备注；按 `Enter` 发送。 |
| `c`      | 对选中的行或行范围发表评论。                                                          |
| `y`      | 将完整计划复制到剪贴板。                                                                 |
| `q`      | 退出计划——不批准计划并关闭计划模式。                              |

按 `Tab` 可在计划预览与提示框之间移动焦点。

计划批准视图打开时，在按 `a` 批准前，`Ctrl+P`（命令面板 → model）仍可用于切换模型。

<a id="providing-feedback"></a>
### 提供反馈

批准视图有三种焦点状态：

- **预览**：滚动计划，并选择要发表评论的行。
- **评论**：为选中的行范围添加内联评论（按 `c`，或在某一行按 `Enter`）。
- **提示框**：输入自由格式的修订备注。

按 `Tab` 可在预览与提示框之间切换。发送反馈时——无论是内联评论、自由格式备注，还是两者兼有——代理都会收到反馈并修订计划。计划模式会保持活动状态，方便你迭代。 输入框中完整的界面命令（例如 `/feedback <text>` 或 `/compact`）会作为命令执行，不作为修订备注发送，审核视图保持打开。输入框仍有此类命令时，按 `a` 批准会被拒绝；先按 Enter 执行命令或将其删除。

<a id="leaving-the-approval-view"></a>
### 离开批准视图

按 `Esc` 可将焦点从提示框移回计划预览。若要在不批准或发送反馈的情况下关闭批准界面，按 `q` 退出计划。退出会放弃拟定的计划并关闭计划模式。

<a id="plan-mode-lifecycle"></a>
## 计划模式生命周期

计划模式状态机有四种状态：

| 状态          | 描述                                                    |
| -------------- | -------------------------------------------------------------- |
| `Inactive`     | 普通运行模式。没有计划模式约束。               |
| `Pending`      | 客户端已将计划模式切换为开启，但尚未发送提示。  |
| `Active`       | 计划模式已启用。计划文件编辑会自动获批；其他文件的编辑会被拒绝。 |
| `ExitPending`  | 回合进行中时，用户将计划模式切换为关闭。          |

状态转换：

```
Inactive    --> Active   （调用并批准 enter_plan_mode 工具 —— 跳过 Pending）
Inactive    --> Pending  （你通过 /plan 或 Shift+Tab 开启计划模式）
Pending     --> Active   （你的第一条提示激活计划模式）
Active      --> Inactive （批准 exit_plan_mode，或空闲时将计划模式切换为关闭）
Active      --> ExitPending （回合进行中时将计划模式切换为关闭）
ExitPending --> Inactive （回合完成后）
```

计划模式状态会持久化到磁盘，并在进程重启后保留。瞬态状态（`Pending`、`ExitPending`）会在重启时折叠为 `Inactive`，因为它们依赖正在进行的交互。

<a id="edits-during-plan-mode"></a>
## 计划模式期间的编辑

计划模式活动期间，计划文件的编辑会自动获批且不提示，因此代理可以自由迭代计划。**任何其他文件的编辑都会在执行前被拒绝**——代理会收到一条简短消息，其中指出计划文件是唯一可编辑路径。

这项强制规则独立于权限模式：

- **始终批准（yolo）会在计划模式下保持启用。** 非编辑工具（bash 命令、读取、MCP 工具）仍会自动运行，但文件编辑会被阻止，直到你批准退出计划模式。计划获批后，始终批准模式会恢复用于实现。
- 不会检查 Bash 命令是否写入文件——计划模式阻止的是编辑工具，而不是 Shell 重定向。
- 父会话的计划模式编辑门禁不涵盖子代理。每个子代理都会以全新的计划模式跟踪器（`Inactive`）启动，因此 `general-purpose`（或其他具有写入能力的）子代理可以在父会话仍处于计划模式时编辑文件；同时它会继承父会话的权限模式（包括始终批准）。`explore` 等只读类型仍受自身工具集限制。

计划模式活动时，状态标志显示为 `plan`。如果其下方启用了始终批准，退出计划模式后会再次显示该标志。

<a id="plan-mode-and-compaction"></a>
## 计划模式与压缩

活动计划模式会话中运行 `/compact` 时，计划模式状态会保留。压缩后的上下文会包含计划模式仍处于活动状态的提醒，因此代理会在压缩后继续规划。

---

<a id="when-plan-mode-is-appropriate"></a>
## 何时适合使用计划模式

**使用计划模式：**

- 存在重大架构歧义的任务（有多种合理方案）
- 需求不明确，需要先探索再实现
- 影响面大的重构，错误方案会浪费大量工作

**跳过计划模式：**

- 实现路径清晰的任务
- 只要理解问题就能明显确定修复方式的缺陷
- 遵循现有约定即可添加的功能
- 直接的修改（重命名、格式化、添加测试）
- 研究和探索任务（改用子代理）
